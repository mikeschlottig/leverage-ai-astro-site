## 5 Additional Game-Changing Plugins

The six already proposed cover the obvious WordPress replacements. These five go further and exploit what makes EmDash *uniquely* powerful — the Cloudflare stack, Portable Text, the MCP server, and the Durable Objects model that WordPress could never touch.

---

### 1. `emdash-vector-search` — Semantic + Hybrid Content Search
**The gap WordPress never filled.** WordPress search is a `LIKE %query%` query. This replaces it with real intelligence.

**Type:** Standard  
**Capabilities:** `read:content`, `kv:write`, `network:fetch`

**Architecture:**
- `content:afterSave` hook → generates embeddings via **Workers AI `bge-m3`** → stores vectors in **Cloudflare Vectorize**
- Search route `/search/semantic` → hybrid query: D1 FTS5 (BM25 keyword ranking) + Vectorize ANN (cosine similarity) → merged ranked results
- KV caches hot queries with TTL

**Why game-changing:** Every content site needs search. This gives EmDash semantic search that rivals Algolia — with zero external SaaS, zero per-search cost beyond Workers AI, and full data sovereignty. The embeddings pipeline runs in the same Cloudflare account as everything else. Astro theme components query the route; zero client JS needed.

---

### 2. `emdash-edge-personalization` — Durable Object-Backed Content Variants
**This is the one WordPress physically cannot do.**

**Type:** Native (needs Durable Objects binding)  
**Capabilities:** `read:content`, `write:content`, `auth:read`

**Architecture:**
- A `PersonalizationAgent` Durable Object maintains user segment state (geo, device, visit count, tier, tags)
- `content:beforeRender` hook (or a Astro middleware layer) swaps Portable Text block variants based on segment
- Admin UI (React): visual A/B test builder — create content variants per segment, set traffic splits, set goals
- Results aggregated back to D1 via `content:afterView` hook → live conversion dashboard widget

**Why game-changing:** True edge personalization at P0 latency — no round-trip to origin, no JS flicker. A CMS that personalizes content before the HTML hits the wire is a completely different product category than WordPress. Pairs perfectly with the analytics plugin already proposed.

---

### 3. `emdash-i18n` — AI-Powered Multilingual Content Pipeline
**Type:** Standard + Native companion (translation memory UI)  
**Capabilities:** `read:content`, `write:content`, `network:fetch`, `kv:read`, `kv:write`

**Architecture:**
- Extends content collections with locale variants (slug-per-locale in D1, same `collectionId` foreign key)
- `content:afterSave` hook → if source locale, enqueues translation jobs via Workers AI (or Grok) → writes translated variants as draft entries
- KV translation memory: stores segment→translation pairs, dedupes repeated phrases across content
- Admin dashboard widget: translation status per collection, approve/reject AI translations
- Astro routing integration: `[locale]/[slug].astro` pattern, `hreflang` injection, RTL stylesheet toggling

**Why game-changing:** Multilingual is one of the top-3 reasons enterprises stay on complex CMSes. This makes it a checkbox feature for EmDash, with AI doing 90% of the work. Translation memory means cost drops with scale.

---

### 4. `emdash-og-forge` — Dynamic Visual Identity at the Edge
**Type:** Standard  
**Capabilities:** `read:content`, `network:fetch`, `read:media`

**Architecture:**
- On-demand route `/og/:contentSlug.png` → fetches content metadata → renders OG image via **Cloudflare Images** transform (or `@resvg/resvg-wasm` for SVG-to-PNG in Workers)
- Template system in plugin settings: brand colors, fonts, layout presets (text overlay, featured image crop, logo placement)
- `content:afterSave` hook → pre-warms OG image for published content via `ctx.http.fetch` to the route
- Injects `<meta og:image>` + JSON-LD structured data (Article, BreadcrumbList, Organization) via Astro head slot

**Why game-changing:** Every content piece gets a pixel-perfect, brand-consistent social card automatically. JSON-LD structured data is critical for Google rich results and AI answer engines (SGE/Perplexity). This replaces a $50/month SaaS (Bannerbear, Placid) with a zero-cost Worker.

---

### 5. `emdash-crm-bridge` — Bidirectional Content-to-CRM Pipeline
**Type:** Standard  
**Capabilities:** `read:content`, `write:content`, `network:fetch`, `email:send`, `kv:read`, `kv:write`

**Architecture:**
- Maps EmDash content events to CRM actions via a rules engine (configured in Block Kit admin)
- Form submissions (pairs with first-party forms plugin) → create/update CRM contacts
- Content engagement events → lead scoring updates in KV → sync threshold triggers to CRM
- Outbound: CRM deal stage changes → trigger gated content access updates in membership plugin
- Supports HubSpot, Salesforce (REST v2), and a generic webhook target for custom CRMs
- `allowedHosts` scoped to exactly the CRM domains declared in settings

**Why game-changing:** This turns EmDash into the source of truth for content-driven lead gen — which is exactly the use case your SMB clients have. Content → capture → qualify → CRM, fully automated, no Zapier needed. Plugin communicates only with explicitly declared hosts, making it auditable for SOC2-adjacent compliance.

## CLI Brief: Reusable Components, Libraries, and Pages

EmDash's CLI (`emcli`) plus the MCP server are the real unlock for reusability at scale. Here's how to structure it:

**Scaffolding workflow with `emcli`:**
```bash
# Scaffold a new reusable plugin
npx emcli generate plugin emdash-vector-search --type=standard

# Scaffold a page template
npx emcli generate page blog/[slug] --collection=posts

# Scaffold a component
npx emcli generate component PostCard --portable-text-block
```

**Component library architecture** (what you should build once, reuse everywhere):

```
src/
├── components/
│   ├── index.ts              ← barrel export — import everything from here
│   ├── blocks/               ← Portable Text block renderers
│   │   ├── HeroBlock.astro
│   │   ├── TestimonialBlock.astro
│   │   └── CTABlock.astro
│   ├── patterns/             ← composed multi-component patterns
│   │   ├── BlogIndexLayout.astro
│   │   └── ProductGrid.astro
│   └── primitives/           ← atoms (Button, Card, Badge)
└── live.config.ts            ← global query defaults here, once
```

The barrel `index.ts` + `live.config.ts` is the key. Every page imports from `../components` (single source), every query defaults from `live.config.ts` (single config). When you add a new collection, one entry in each file and it's available everywhere.

**For plugin reuse across client projects:** Package each plugin as a scoped npm package (`@leverageai/emdash-vector-search`), publish to your private registry (or GitHub Packages), and `npm install` into any EmDash project. The seed file ships with the package — one install, one admin wizard run, full feature.

**MCP server automation:** EmDash's built-in MCP server exposes content schema + collection CRUD. Wire it into Claude Code with a `CLAUDE.md` that describes your component patterns — then your agents can scaffold new pages by reading live collection schemas and generating typed Astro components automatically.

## Automated Setup (Already on Cloudflare)

Since your D1/R2/Workers infrastructure is already provisioned, here's the exact path:

**Step 1: Create the EmDash project wired to your existing resources**

```bash
npm create emdash@latest my-site -- --template=cloudflare-blog
cd my-site
```

**Step 2: `wrangler.jsonc` — point at your existing bindings**

```jsonc
{
  "name": "my-emdash-site",
  "main": "./dist/_worker.js",
  "compatibility_date": "2025-01-01",
  "assets": { "directory": "./dist" },
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "your-existing-db-name",
      "database_id": "your-existing-db-id"
    }
  ],
  "r2_buckets": [
    {
      "binding": "MEDIA",
      "bucket_name": "your-existing-r2-bucket"
    }
  ],
  "kv_namespaces": [
    {
      "binding": "KV",
      "id": "your-existing-kv-id"
    }
  ]
}
```

**Step 3: `astro.config.mjs` — wire EmDash integration**

```ts
import { defineConfig } from "astro/config";
import cloudflare from "@astrojs/cloudflare";
import emdash from "emdash/astro";

export default defineConfig({
  output: "server",
  adapter: cloudflare({ mode: "directory" }),
  integrations: [
    emdash({
      db: { binding: "DB" },
      storage: { binding: "MEDIA" },
      kv: { binding: "KV" },
      plugins: [],       // add plugins here as you build them
    }),
  ],
});
```

**Step 4: Seed file** — drop your schema into `.emdash/seed.json`, modeled on whatever collections your clients need. This runs once on first admin visit.

**Step 5: Deploy + first-run wizard**

```bash
npm run build
wrangler deploy

# First visit to /admin triggers the setup wizard
# Creates tables in your existing D1, configures R2 for media
# One-time operation — idempotent after that
```

**Step 6: Automation script** — for spinning up new client sites against the same Cloudflare account:

```bash
#!/bin/bash
# new-client-site.sh
CLIENT=$1
npx create emdash@latest $CLIENT -- --template=cloudflare-blog
cp templates/seed.json $CLIENT/.emdash/seed.json
cp templates/wrangler.template.jsonc $CLIENT/wrangler.jsonc
sed -i "s/CLIENT_NAME/$CLIENT/g" $CLIENT/wrangler.jsonc

cd $CLIENT
wrangler d1 create ${CLIENT}-db
wrangler r2 bucket create ${CLIENT}-media
npm install && npm run build && wrangler deploy

echo "✅ $CLIENT deployed. Hit /admin to complete setup."
```
