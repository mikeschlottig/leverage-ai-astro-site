A comprehensive implementation guide for building stateful, memory-augmented AI agents using Hermes Agent (Nous Research) and Honcho (Plastic Labs). Covers architecture, integration patterns, real-world use cases, and a phased build roadmap.

Hermes Agent v0.x  ·  Honcho v3.0.3  ·  March 2026

01 What They Are

These two open-source projects sit in complementary layers of an agentic stack. Understanding the division of responsibility is the first step before building anything.

Agent Runtime
Hermes Agent
An open-source AI agent from Nous Research. It handles tool execution, terminal access, multi-platform messaging, scheduling, and LLM provider routing. Think of it as the agent's body — what it can do and where it lives.

GitHub: NousResearch/hermes-agent
Docs: hermes-agent.nousresearch.com/docs
Memory Layer
Honcho
An open-source memory library from Plastic Labs with a managed service. It provides persistent cross-session memory, formal logical reasoning over interactions, and peer modeling for any entity. The agent's long-term brain.

GitHub: plastic-labs/honcho
Docs: docs.honcho.dev
ⓘ
Hermes natively integrates Honcho as an optional memory backend. You can use either tool independently, but together they form a full stateful agent stack — execution layer + persistent memory layer — without building the plumbing yourself.

The Core Problem They Solve Together

Standard LLM chat is stateless. Every session starts cold. Users re-explain their context, preferences, and history every conversation. For agents deployed across Telegram, Discord, or CLI sessions that run for weeks, this is a fundamental limitation.

02 Architecture

Hermes Architecture

Hermes is a Python-based agent runtime built on an agent loop pattern. The core components:

Agent Loop
Receive message → select tools → call LLM → execute tools → repeat until done. Interruptible mid-loop by new input.
Tool System
40+ built-in tools. Terminal backend (local, Docker, SSH). Web search, file ops, browser, code execution.
Gateway
Multi-platform messaging layer. Normalizes Telegram, Discord, Slack, WhatsApp, Signal, Email into a single agent surface.
Skills System
Procedural memory as Markdown files. Installable from the hub, custom, or well-known endpoints. Injected as context.
Sessions
Persistent conversation threads. Context, MEMORY.md, USER.md survive restarts. Per-directory or global scope.
ACP/MCP
Runs as ACP server for VS Code/Zed/JetBrains. Connects any MCP server for extended capabilities.

Honcho Architecture

Honcho is a FastAPI server with a PostgreSQL + pgvector backend. Its data model centers on a peer paradigm where both users and AI agents are first-class entities.

Workspaces
├── Peers  (users, agents, any entity)
│   ├── Sessions  (conversation threads)
│   └── Collections
│       └── Documents  (vector-embedded data)
│
└── Sessions (many-to-many with Peers)
    └── Messages  (attributed to a Peer)

Behind this storage layer, a deriver background worker processes messages asynchronously:

  1. Messages arrive via API
  2. Derivation tasks enqueued (representation update, session summary)
  3. Formal logical reasoning extracts premises → conclusions
  4. Representations stored in reserved Collections per peer
  5. Available instantly via peer.chat() or session.context()

Two Memory Layers (Hybrid Mode)

Layer Scope Use For Managed By
Local session history Current conversation only Recent context, follow-ups, task state Hermes (MEMORY.md / USER.md)
Honcho memory All sessions, all time Preferences, project facts, personality modeling Honcho deriver (background)

03 Integration Model

Dual-Peer Architecture

When Hermes connects to Honcho, both the user and the agent get peer representations. This is not the typical "user profile" pattern — both sides are modeled and injected into context.

User Peer
Observed from user messages. Learns: preferences, communication style, goals, project context, recurring patterns. Updated continuously as conversations accumulate.
AI Peer (Hermes)
Observed from assistant messages. Builds the agent's own knowledge representation — what it knows, how it's been responding, its accumulated understanding of the user's domain.

Both representations are injected into the system prompt before each response, giving Hermes awareness of who it's talking to and what it already knows from prior sessions.

The Four Honcho Tools in Hermes

Tool Latency What It Returns Best For
honcho_profile Low Peer card — curated key facts, no LLM Fast context injection at session start
honcho_search Low–Med Semantic search results over memory Finding specific past facts or preferences
honcho_context Med–High Dialectic Q&A — synthesized answers via LLM Complex questions about the user's situation
honcho_conclude Write Stores durable facts back to Honcho Explicit preferences, corrections, key context

Session Scoping Strategies

Strategy Config Best For
Per-Session New Honcho session each Hermes session Chat apps, general assistants
Per-Directory Session ID tied to working directory Coding assistants, project-scoped agents
Global Single Honcho session for user+agent pair Personal agents with full continuity across all contexts

Security Model

Hermes has a layered security model critical for production deployments:

  • Command approval: Configurable approval flow before executing terminal commands
  • Docker isolation: hermes config set terminal.backend docker sandboxes all shell access
  • SSH backend: Route terminal execution to a remote server, keeping local machine clean
  • DM pairing: Messaging gateway requires cryptographic pairing before accepting commands
  • Container isolation: Full sandboxed mode for untrusted workloads

06 Honcho — Installation

Managed Service (Fastest)

Sign up at app.honcho.dev. Every new tenant gets $100 in free credits. No infrastructure to manage.

python Managed service quickstart
pip install honcho-ai
# Or: uv add honcho-ai | poetry add honcho-ai
python Python SDK — 5-minute example
from honcho import Honcho

# 1. Init client with your workspace
honcho = Honcho(workspace_id="my-app", api_key=HONCHO_API_KEY)

# 2. Create peers (users AND agents are peers)
user = honcho.peer("alice")
agent = honcho.peer("assistant")

# 3. Create session and add messages
session = honcho.session("session-001")
session.add_messages([
    user.message("I'm building a personal finance app with Honcho"),
    agent.message("That's a great use case for persistent memory!"),
])

# 4. Query for insights (after background reasoning completes)
response = user.chat("What should I know about this user? 3 sentences max")
print(response)

07 Honcho — Core Primitives

Workspaces
Top-level isolation boundary. Create one per application, product line, or tenant group. Provides multi-tenancy at the data layer.
Peers
Any entity that persists and changes over time — users, agents, teams, ideas. Unified model for human and AI participants. Both sides of a conversation get peer representations.
Sessions
Interaction threads between peers. Many-to-many with peers. Can span multiple human participants and multiple agents in the same conversation context.
Messages
Atomic data units attributed to a specific peer. Processed asynchronously to update peer representations. The raw input for all reasoning.
Collections & Documents
Named groups of vector-embedded data. Used internally for representations and externally for RAG applications. Query with cosine similarity.
Representations
Synthesized conclusions about a peer from a session. Low-latency static documents for fast context injection without an LLM round-trip at inference time.

Reasoning Engine

This is what distinguishes Honcho from simple message storage. The background deriver runs multi-step formal reasoning:

Input
Messages
Any peer's messages
Step 1
Premises
Extract stated facts
Step 2
Conclusions
Logical inference
Step 3
Representations
Stored in Collections
Output
Peer Model
Queryable via API

The reasoning goes beyond what's explicitly stated. If a user spends 80% of a conversation on a side project and mentions "I wish I had more time for this" — Honcho concludes they're motivated and constrained, not just that they have a side project.

Query Patterns

python All four retrieval methods
# 1. Dialectic chat — natural language Q&A about a peer (LLM-powered)
response = user.chat("What are this user's communication preferences?")

# 2. Session context — for feeding to your LLM (up to token limit)
context = session.context(summary=True, tokens=10_000)
openai_messages = context.to_openai(assistant=agent)  # Format conversion

# 3. Semantic search — hybrid vector + keyword over messages
results = user.search("project architecture decisions")

# 4. Representations — fast static doc, no LLM call at query time
rep = session.representation(user)   # Session-scoped peer summary
peer_card = user.peer_card()          # Global peer summary

Choosing the Right Query Method

MethodLatencyUse When
peer_card()~50msFast context injection at session start
representation()~100msSession-specific context, no LLM wait
search()~200msLooking up specific facts, preferences, past decisions
chat()1–3sComplex synthesis, "what should I know about X user", personalization
context()~150msLong-running conversations, feed to your own LLM

09 Use Case: Telegram Bot with Memory

Deploy Hermes as a Telegram bot that builds a persistent model of each user it talks to — no re-introductions needed after the first conversation.

Setup steps

  1. Create a Telegram bot via BotFather, get token
  2. Run hermes gateway setup, select Telegram
  3. Configure Honcho with per-user peer scoping
  4. Set memory mode to hybrid
  5. Deploy gateway daemon (systemd or Docker)

Memory scoping

Each Telegram user ID becomes a Honcho peer ID. All their sessions accumulate into a single peer representation — the bot remembers each user independently.

python Custom Telegram + Honcho bot
from honcho import Honcho
from telegram.ext import Application

honcho = Honcho(workspace_id="my-bot")

async def handle_message(update, context):
    user_id = str(update.effective_user.id)

    # Get or create peer for this user
    user = honcho.peer(user_id)
    agent = honcho.peer("bot")
    session = honcho.session(f"tg_{user_id}_current")

    # Get user context (fast, no LLM call)
    profile = user.peer_card()

    # Build prompt with memory context
    system = f"User context: {profile}\n\nRespond helpfully."

    # ... call your LLM, get response ...

    # Store messages in Honcho
    session.add_messages([
        user.message(update.message.text),
        agent.message(bot_response),
    ])

10 Use Case: CRM + Memory Layer

Use Honcho as a memory substrate for a CRM or sales tool. Every interaction with a lead or customer builds a persistent, reasoned model of that person — far richer than static CRM fields.

Traditional CRM
Static fields: name, company, last contact date, deal stage. Reps must manually update notes. Context lost between calls. New rep starts from scratch.
Honcho-augmented CRM
Dynamic peer model: communication style, decision-making patterns, stated objections, inferred priorities, relationship history. Automatically built from every interaction.
python CRM peer modeling example
# Each lead/customer is a Honcho peer
lead = honcho.peer("lead_john_acme")
rep = honcho.peer("rep_sarah")

# After a sales call, ingest the transcript
session = honcho.session("call_2026_03_15")
session.add_messages(transcript_messages)

# Before next call — get synthesized context
briefing = lead.chat(
    "What are this lead's main objections, decision criteria, "
    "and what's the best angle for the next call?"
)

# Search for specific past discussions
pricing_discussions = lead.search("pricing budget timeline")

# Get full rep + lead representations for CRM dashboard
lead_context = session.representation(lead)
rep_context = session.representation(rep)

Combining Hermes for orchestration and Honcho for memory to run a personalized cold email pipeline. Relevant for the law firm targeting / Scorpion replacement use case.

typescript TypeScript pipeline with Honcho SDK
import { Honcho } from '@honcho-ai/sdk';

const honcho = new Honcho({ workspaceId: 'legal-outreach' });

async function processProspect(firm: LawFirm) {
    const prospect = honcho.peer(firm.domain);

    // Ingest all scraped data as messages
    const session = honcho.session(`research_${firm.domain}`);
    session.addMessages([
        prospect.message(`Website: ${firm.websiteAnalysis}`),
        prospect.message(`Practice areas: ${firm.practiceAreas}`),
        prospect.message(`PPC spend: ${firm.spyfuData.monthlySpend}`),
        prospect.message(`Reviews: ${firm.reviewSummary}`),
    ]);

    // Wait for reasoning, then generate personalized email
    const angle = await prospect.chat(
        "What's the most compelling GEO value prop for this firm? " +
        "What pain points do their reviews reveal? Be specific."
    );

    // Use angle to generate email with Claude Haiku
    return await generateEmail(firm, angle);
}
↗
Each prospect becomes a Honcho peer. As they reply and engage, their representation updates. Follow-up emails get progressively more personalized as Honcho reasons over the growing interaction history.

13 Use Case: Multi-Agent Fleet with Shared Memory

For fleets of agents operating in parallel — different agents share peer representations to avoid redundant reasoning and maintain consistent context.

Architecture Pattern
Multiple agents as Honcho peers in a shared workspace. Each agent observes and contributes to shared sessions. Orchestrator queries cross-agent representations to coordinate work.
python Multi-agent shared workspace
# All agents share a workspace
honcho = Honcho(workspace_id="agent-fleet")

# Each agent is a peer
researcher = honcho.peer("researcher-agent")
writer = honcho.peer("writer-agent")
reviewer = honcho.peer("reviewer-agent")
orchestrator = honcho.peer("orchestrator")

# Shared session — all agents participate
task_session = honcho.session("task-blog-post-001")
task_session.add_peers([researcher, writer, reviewer, orchestrator])

# Researcher stores findings
task_session.add_messages([
    researcher.message("Found 3 key studies on X. Key finding: ..."),
])

# Writer queries what researcher found before writing
research_context = researcher.search("key findings for blog post")

# Orchestrator queries cross-agent status
task_status = orchestrator.chat(
    "What has each agent completed? What's blocking the task?"
)
ⓘ
Honcho's peer paradigm makes multi-agent architectures first-class. Both human users and AI agents are modeled identically — any peer can observe any other peer, configurable per session with observe_me and observe_others flags.

14 Developer Roadmap

A phased implementation path from zero to a production multi-agent system with persistent memory.

1
Phase 1 — Foundation (Day 1–3)
Single agent, local everything
Get Hermes running locally with your preferred LLM provider. Understand the tool system, test basic terminal and web access. No memory integration yet — focus on agent loop fundamentals.
  • Install Hermes via one-line installer
  • Configure LLM provider (hermes model)
  • Enable Docker sandbox backend for safety
  • Test terminal tools, web search, file operations
  • Install 2–3 relevant skills from the hub
  • Sign up at app.honcho.dev, get API key
  • Run the Honcho Python quickstart, verify reasoning output
2
Phase 2 — Memory Integration (Day 4–7)
Connect Hermes to Honcho, verify cross-session recall
Wire up the ~/.honcho/config.json integration. Run the canonical cross-session recall test. Understand how the four Honcho tools are used by the agent, and when each fires.
  • Configure ~/.honcho/config.json pointing at managed or local Honcho
  • Run hermes honcho status — verify connection
  • Run cross-session recall test ("velvet circuit" pattern)
  • Test writeback: tell agent a preference, open fresh session, verify recall
  • Observe which Honcho tools fire naturally (profile, search, context, conclude)
  • Test all three session scoping strategies: per-session, per-directory, global
3
Phase 3 — Multi-Platform Deployment (Week 2)
Gateway + cron + voice
Extend the agent to your messaging platforms of choice. Add scheduled tasks. Enable voice mode if running on mobile. Deploy the gateway as a persistent daemon.
  • Run hermes gateway setup, configure Telegram (primary) + one other
  • Test DM pairing security flow
  • Create first cron task: morning briefing to Telegram
  • Install and test voice mode (Ctrl+B to record)
  • Configure SSH or Docker backend for gateway-triggered commands
  • Systemd service or Docker Compose for persistent gateway
4
Phase 4 — Production Hardening (Week 3–4)
Self-hosted Honcho, custom skills, multi-agent
Move to self-hosted Honcho for data ownership. Build custom skills for your domain. Implement multi-agent coordination patterns. Add MCP servers for extended capabilities.
  • Deploy Honcho via Docker Compose on mini PC or VPS
  • Configure Postgres with pgvector (local or Supabase)
  • Run migrations, verify deriver is processing
  • Write custom skills for your specific domain
  • Add MCP servers to ~/.hermes/config.yaml
  • Implement multi-peer session pattern for agent coordination
  • Monitor queue status: session.queue_status()
  • Build peer.chat() powered dashboards over Honcho API

15 Design Patterns

Pattern 1: Lazy Context Injection

Don't always call peer.chat() — it has LLM latency. Use the right retrieval method for the latency budget:

python Tiered retrieval pattern
async def build_prompt(user_peer, session, user_message):
    # Always: fast peer card (no LLM, ~50ms)
    profile = user_peer.peer_card()

    # Conditionally: semantic search if topic-specific
    if is_topic_specific(user_message):
        relevant = user_peer.search(user_message)
        context = f"{profile}\n\nRelevant history:\n{relevant}"
    else:
        context = profile

    # Rarely: full dialectic synthesis for complex personalization
    if needs_deep_context(user_message):
        synthesis = await user_peer.chat(f"Given: {user_message}, what context matters?")
        context = f"{context}\n\nSynthesis: {synthesis}"

    return context

Pattern 2: GED-Aware Agent Sessions

For complex multi-session projects managed via a Guided Execution Document, use Honcho to store the GED state as a peer's document collection — survives context wipes:

python GED state persistence
# Store GED as a document in the agent peer's collection
agent = honcho.peer("claude-code-agent")
project_collection = agent.collection("ged-state")

# On session start, retrieve current GED
ged_docs = project_collection.query("current project state and next steps")

# On session end, update GED in Honcho
project_collection.add_document(
    content=updated_ged_markdown,
    metadata={"phase": current_phase, "timestamp": now()}
)

Pattern 3: Observation Control in Multi-Agent Sessions

In multi-agent pipelines, you often don't want every agent modeling every other agent. Control observation explicitly:

python Selective peer observation
# Add peers with observation flags
session.add_peer(user, observe_me=True, observe_others=False)   # Model user
session.add_peer(agent, observe_me=False, observe_others=True)  # Agent observes user
session.add_peer(reviewer, observe_me=False, observe_others=False) # Reviewer: no observation

Pattern 4: Streaming Responses with Memory

python Streaming with Honcho context
async for chunk in session.stream(
    query="Continue our discussion about the architecture",
    peer=agent,
    context_tokens=8000
):
    print(chunk, end="", flush=True)
